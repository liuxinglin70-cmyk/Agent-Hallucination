# 下一步预测机制审计 - 执行摘要

**审计日期**: 2026-10-17  
**审计对象**: 下一步预测机制两轮迭代优化验证  
**核心问题**: 为何接入后精度下降？是设计问题还是实施问题？

---

## 一、核心发现

### 精度变化
相对最近基线（2026-10-15），接入下一步预测后：
- ✅ 权威覆盖：99% → 100%（+1%）
- ❌ 检测精度：76/100 → 76/100（净增益**0**）
- ❌ 定位精度：27/62 → 27/62（净增益**0**）
- ❌ 成本增加：请求+7.7%，耗时+22.7%

### 根本原因判断

**结论：不是设计问题，是实施缺陷**

✅ **机制设计合理**：
- 前缀隔离正确（未泄露未来信息）
- 权限分离正确（预测无独立判定权）
- 预算控制正确（在可选额度内）
- 集成流程清晰（6步流程验证通过）

❌ **三大实施缺陷导致机制失效**：

1. **预算计算过度保守**（最严重）
   - 错误：预留 `3×votes` 倍额度，实际只需 `1×`
   - 后果：23/100 案例因预算耗尽未生成预测
   - 影响：预测生成成功率应为90%+，实际仅72%

2. **有效覆盖严重不足**
   - 43/100 案例接受预测
   - 但代表票中仅 8/43（18.6%）为有效比较（matched/divergent）
   - 其余 35/43（81.4%）为 unknown（信号丢失）

3. **比较验证过严**
   - 引用必须逐字匹配原文，容易失败
   - 前缀只保留最近6个事件，早期上下文丢失
   - 时序判断要求过高，模型倾向返回 unknown

**类比理解**：就像一个设计优秀的传感器，但因为校准错误（预算）、信号处理不当（验证过严）、采样率不足（前缀太短），导致输出噪声过大而无法使用。

## 四、解决方案（分优先级）

### 🔴 P0：立即修复（1-2天）

#### 修复1：纠正预算计算
**位置**: `detector/judge.py` 第383行  
**错误**: 
```python
reserve_context((forecast_block + extension) * votes)  # 错误：×3
```
**修正**:
```python
reserve_context(forecast_block + extension)  # 正确：×1
```
**预期收益**: 预测生成成功率 72% → 90%+

#### 修复2：优化比较验证
- 放宽引用匹配：允许子串模糊匹配（≥10字符）
- 增加前缀保留：从6个事件增至10-12个
- 简化验证流程：合并过度细分的失败类型

**预期收益**: 有效比较占比 18.6% → 40%+

#### 修复3：修复候选生成
**位置**: `detector/action_evidence.py`  
**问题**: 当 `forecast_used=False` 时返回空列表  
**修正**: 即使未发送，预测对象存在时仍应收集候选

### 🟡 P1：短期优化（3-5天）

1. 增加预测约束数量：2个 → 3-4个
2. 改进候选选择逻辑：统一为单层评分排序
3. 添加修复尝试限制：避免无效修复的成本

### 🟢 P2：中期改进（1-2周）

1. A/B对照实验：同源码、同预算的 on/off 消融
2. 共享规则学习：离线提取高频错误模式
3. 严格微事件时序：精确建模 action → observation 因果链
