## 执行摘要

### 核心发现

**精度变化**: 相对最近基线（2026-10-15），接入下一步预测后的实验结果（2026-10-16）显示：
- 检测精度：4例修正 / 4例回退，**净增益为0**
- 定位精度：2例修正 / 2例回退，**净增益为0**
- 权威覆盖：99/100 → 100/100（+1%）

**成本变化**:
- 采用路径请求数：740 → 797（+7.70%）
- 案例中位耗时：787.6秒 → 966.6秒（+22.73%）
- 全部尝试请求数：866 → 940（+8.55%）

**机制覆盖**:
- 43/100 案例接受并发送模型预测
- 代表票中有效比较：matched 5、divergent 3、**unknown 35**
- 预测健康状态：ok 72、budget_exhausted 23、contract_error 3、provider_error 2

### 结论判断

**精度下降的根本原因不是机制设计本身有问题，而是实施层面的多个技术障碍导致机制未能充分发挥作用：**

1. **有效覆盖不足**（最严重）：43例接受预测，但代表票中仅8例为非unknown比较（18.6%），大量预测未能转化为有效信号
2. **预算计算过度保守**：预算预检逻辑存在2倍过度估算，导致23例因预算耗尽而未生成预测
3. **比较质量问题**：模型生成的比较中，大量被标记为unknown或验证失败，引用、时序、语义判断存在不确定性
4. **增量成本显著**：中位耗时增加22.73%，但未带来精度收益，成本效益不成立

**两轮迭代优化验证过程**:
- 第一轮：技术预试发现JSON转义引文误拒问题，整批82请求被排除
- 第二轮：修复后完成100例+4例恢复，但精度仍持平

**判断**: 机制设计合理，但工程实施存在关键缺陷，导致"设计有潜力但实际表现不佳"。

## 2. 精度下降根因深度分析

### 2.1 配对变化详细分析

**相对最近基线（2026-10-15）**:

| 类型 | 案例数 | 案例ID示例 |
|------|--------|-----------|
| 检测修正 | 4 | OpenDeepSearch/027, SmolAgents/043, OpenManus/095, Camel/012 |
| 检测回退 | 4 | BFCL/071, OpenDeepSearch/034, OpenManus/031, SmolAgents/062 |
| 定位修正 | 2 | （见comparison.json） |
| 定位回退 | 2 | （见comparison.json） |

**净变化**: 检测 +4-4=0，定位 +2-2=0

**关键观察**:
1. 修正和回退数量完全抵消，呈现"零和游戏"特征
2. 三个divergent案例（OpenDeepSearch/007, SmolAgents/048, SmolAgents/066）在基线中已被检出，本轮未因预测改变结果
3. 权威覆盖增加1%，但新增可判案例未带来更多正确判断

### 2.2 有效覆盖不足（最严重问题）

**数据事实**:
```
接受模型预测: 43/100 案例
代表票有效比较: matched 5 + divergent 3 = 8 (18.6%)
代表票unknown: 35 (81.4%)
```

**问题拆解**:

#### 2.2.1 预测生成阶段损失
```
模型预测请求: 55 (53首轮 + 2恢复)
预测健康ok: 72
预测健康失败: 
  - budget_exhausted: 23例 (32%)
  - contract_error: 3例
  - provider_error: 2例
```

**分析**: 28例（28%）在预测生成阶段就失败，未产生任何约束。

#### 2.2.2 比较验证阶段损失

**所有投票的模型比较统计**:
```
total: 129 条比较
  - matched: 16 (12.4%)
  - divergent: 10 (7.8%)
  - unknown: 103 (79.8%)
```

**代表票的模型比较统计**:
```
total: 43 条比较
  - matched: 5 (11.6%)
  - divergent: 3 (7.0%)
  - unknown: 35 (81.4%)
```

**unknown的细分原因**（根据 action_comparisons 验证逻辑）:
1. **模型明确返回unknown**: 语义不确定、证据不足
2. **验证失败被降级为unknown**:
   - `quote_not_in_action`: 引用文本未在动作通道中找到
   - `invalid_refs`: 证据引用超出范围或格式错误
   - `future_reason_reference`: 理由引用了未来事件
   - `invalid_quote`: 引用与位置不匹配
   - `missing`: 模型未提供比较

**问题根源**:
- **前缀截断导致信息丢失**: `prefix_view()` 只保留最近6个事件，早期关键上下文被省略
- **引用复杂性高**: 模型需要精确引用 `actual_action.channels` 中的原文，容易出错
- **时序判断困难**: "混合内容/工具事件的声明顺序未知"，模型难以确定因果关系
- **语义保守**: 提示要求"对象/义务不一致、等价替代未确认时用unknown"

### 2.3 预算计算过度保守

**代码位置**: `detector/judge.py` 第376-384行

```python
def evaluate():
    used = bool(forecast_block)
    budget = current_added_budget()
    if used and budget is not None:
        try:
            votes = max(1, int(route.get("votes", 1) or 1))
            # 问题: 每个投票都会处理 forecast_block，但实际只发送一次
            OptionalBudget(budget, diagnostic_budget_reserve(policy)).reserve_context(
                (forecast_block + FORECAST_JUDGE_EXTENSION) * votes)  # 这里乘以votes
        except AddedBudgetExceeded:
            used = False
```

**问题分析**:
- 预算预检按 `(forecast_block + extension) × votes` 预留
- 默认配置 `votes=3`，意味着预留了3倍的上下文额度
- 实际执行中，`forecast_block` 在3个投票间复用，只产生1倍成本
- 导致预算检查过度保守，**2倍过估算**

**实际影响**:
```
预测健康budget_exhausted: 23例
配置的额度: max_added_prompt_tokens_per_case=60000
```

假设平均 `forecast_block` 大小为 20K tokens：
- 过度保守预检: 20K × 3 = 60K，触发预算上限
- 实际消耗: 20K × 1 = 20K，本应通过

**预估**: 如果修正预算计算，可能将预测生成成功率从 72% 提升至 **90%+**。

### 2.4 比较质量问题

**质量审查发现**（来自 qualitative-review.json）:

1. **借用下游事件**: 部分比较的理由引用了t+1之后的事件，违反"只使用截至真实下一事件的材料"
2. **替代来源不可靠**: "遵循搜索片段的日期可以matched，但不能证明片段事实正确"
3. **粒度不足**: 当前以原始事件为单位，缺少"严格微事件时序"
4. **义务绑定缺失**: 缺少"通用义务绑定和共享规则学习"

**三个divergent案例复核**:
- OpenDeepSearch/007: 预测divergent，但金标第2步 vs 检测第4步，定位未改善
- SmolAgents/048: 预测divergent，定位第2步，与金标一致但基线已检出
- SmolAgents/066: 预测divergent，定位第3步，与金标一致但基线已检出

**结论**: divergent信号未带来新的检测收益，可能原因：
- 预测的约束太局部，未覆盖真正的首错位置
- Judge投票逻辑中，预测信号权重不足以改变裁决

### 2.5 增量成本分析

**请求数增长**:
```
采用路径: 740 → 797 (+7.70%)
全部尝试: 866 → 940 (+8.55%)
```

**新增请求分解**:
- 预测请求: 67 (含预试12 + 正式55)
- 其他新增: 797 - 740 - 55 = 2 (可能是修复或其他诊断)

**耗时增长**:
```
中位数: 787.6秒 → 966.6秒 (+22.73%, +179秒)
p95: 4154.8秒 → 3901.4秒 (-6.10%)
```

**分析**:
- 中位耗时显著增加，说明大多数案例受影响
- p95下降可能因为：某些长尾案例因预算耗尽提前终止预测，反而加快
- 每案例新增约 179秒（~3分钟），主要来自预测请求 + Judge处理时间

**成本效益评估**:
```
成本: +7.70%请求, +22.73%耗时
收益: 0检测增益, 0定位增益
ROI: 负值
```

```python
OptionalBudget(budget, diagnostic_budget_reserve(policy)).reserve_context(
```
