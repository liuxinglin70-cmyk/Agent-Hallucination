# 基于 RSI 的 Harness Agent 自我改进：让能力真正增长

更新日期：2026-09-17。配套资料：[架构](architecture.md)、[当前进展](progress.md)、[真实闭环修复](../reports/evolution_real/fixes.md)。

本文将用户所说的 Herness Agent 按 Harness Agent 理解，即围绕模型组织上下文、工具、工作记忆、执行流程和资源分配的 agent 系统。本文讨论其自我改进机制，新增设计尚未实现；已有运行事实与方案假设分开陈述。

**本次修订重心：从“如何确认候选有效”，转向“系统怎样自主产生、吸收并继续发展有效改进”。** 验证决定哪些变化值得保留；产生变化依赖诊断能力、可修改的执行结构、可继承的经验，以及下一轮真正使用上一轮成果。

## 0. 核心判断与主张

当前系统更接近“在固定检测器旁边寻找干预规则”。要让 Harness Agent 的自我改进生效，需要把它升级为：**能够调查当前版本的失败、试做新的解题过程、将成功过程编译成可执行技能，并修改自身工作流的系统。**

建议以如下循环为主线：

```text
当前版本 H_t 解决任务
  → 发现 H_t 的残余错误、能力缺口与资源浪费
  → 局部试验定位可改变的瓶颈
  → 带工具的改进 agent 试做解决方案
  → 将成功过程编译为工具、技能、上下文策略或工作流补丁
  → 在适用任务上集成、简化并形成 H_(t+1)
  → H_(t+1) 解决更难的任务，也帮助改进下一版 harness
```

这里的“学习”首先发生在运行系统的持久状态中。底座模型权重可以保持不变：通过增加可执行工具、改变信息呈现、组织新的调查步骤和复用有效策略，系统能力仍可能提高。权重训练是后续选项，不是闭环成立的先决条件。

**关键研究假设：由当前版本的失败驱动，先探索成功处理过程，再编译并继承其机制，比直接生成孤立规则更容易获得可累积的幻觉检查能力。** 它可能失败，尤其在底座不能解决局部子问题、缺少必要外部信息或改动无法泛化时；后文明确对应的处理方式。

## 1. 当前闭环为什么难以产生新能力

### 1.1 学习任务仍来自裸底座，而非当前系统的能力前沿

`evolution/engine.py` 的 `preview_cycle` 和正式 cycle 都明确使用 `empty_registry()` 做 patrol，注释说明候选只从裸底座失败中提炼；候选门控则已有在 active registry 上评估增量的逻辑。

这意味着**改进需求的来源与被改进的实际版本不完全一致**：某错误可能已经被上一代修好，却继续主导下一轮提案；新能力之间产生的冲突、当前版本独有的失败、能力组合后才可解决的问题，未成为主要巡检信号。

建议将主巡检改成当前完整版本 `H_t`，保留少量裸底座运行用于长期对照。诊断同时区分“从未会过”“旧能力退化”“技能路由未命中”“技能组合冲突”。开发侧观察 active 版本并不等于标签污染；污染取决于反馈来源是否可靠、是否越过数据边界。当前输出可以作为待诊断行为，不能自产 gold。

### 1.2 proposer 更像格式受限的提案器，缺少完整的改进工作过程

`evolution/proposer.py` 的主要提案协议要求输出干预 JSON，围绕既定 hook、谓词、guard 和 recall trigger，使用失败族摘要及 typed samples。它提供了可执行边界，但也把调查与实现过程压缩成一次格式化提案。

很多有效改动需要先读相关源码、检查具体阶段输入、写一个小型转换工具、运行局部实验，再根据错误修订。仅要求模型在现有字段里写出一条更好的规则，无法表达这些过程。

因此需要新增**带工作区、代码读取、补丁编辑、局部运行和差异检查工具的 improver agent**。现有 JSON proposer 保留为便宜的补丁操作之一，不再承担全部能力发现。

### 1.3 固定执行流程限制了改进类型

当前 `detector/api.py` 编排 judge、recall、upgrade、tracer、defense，`interventions.py` 在既定位置执行干预。可以改阶段提示和局部行为，但尚不能一般性地提出“先拆分断言，再按证据缺口调查”“发现单位歧义时先换算再判定”等流程。

若真实瓶颈是证据没进入上下文，增加 judge 投票并不能补回证据；若问题是推导过程未显式表示，扩大词面谓词也可能没有帮助。**自我改进必须允许修改真正承载瓶颈的组件。**

### 1.4 部分反馈被当成终结理由，没有转化为下一步行动

结构、无害、行为、边际等结果能筛掉不合格候选，却不直接告诉改进 agent：哪个前提缺失、哪个阶段输入不充分、应该先试哪种修改。历史拒绝主要抑制重复提案，也容易把“这个版本失败”混成“这个方向不可修复”。

应把失败转成结构化的差异诊断与下一步试验。存档也应保存成功策略的实现和失败边界，让后代可以修改、组合、重用，而不只是检索拒绝原因。

上述判断基于当前代码结构，是可检查的机制假设；现有真实实验仍未证明改进无效的唯一原因。旧第 1 轮准入 0、原 G 无 FN、后续工程修复未带来新的真实收益记录，不能被改写为新方案已经有效。

## 2. 明确自我改进的对象：一个可编辑、可装载的 Harness

将每代版本表示为：

```text
H_t = (G_t, C_t, T_t, M_t, R_t)
G：工作流与状态转移      C：上下文构造与信息压缩
T：工具和技能实现        M：可检索的经验与技能记忆
R：路由、预算及停止策略
```

底座模型 `B` 执行这些组件组织的任务；改进策略 `I_t` 调查并修改 `H_t`。有效变化必须落到下一轮实际装载的版本，不能只保存在 Markdown 反思或未加载的候选目录。

| 可改对象 | 本项目的具体改动例子 | 产生收益的路径 |
| --- | --- | --- |
| 上下文 C | 按 claim 提取相关事件，保留实体、时间、单位、原始引用；按需展开原文 | 降低无关轨迹干扰，避免截断关键证据 |
| 工具 T | 创建数值推导重建、工具成功状态解析、引用溯源等小程序 | 把模型不稳定的局部操作变成可执行能力 |
| 工作流 G | 拆分断言→建立证据表→只调查未解决断言→绑定原 claim 进入听证 | 减少漏查和跨阶段讨论对象漂移 |
| 记忆 M | 存储“何时使用、如何执行、何时失败”的技能及成功/失败片段 | 新任务复用程序性经验，避免每次重新发现 |
| 策略 R | 根据证据缺口选择专用工具、定向召回、深查或停止 | 将计算花在缺失能力上，降低重复无效调用 |
| 改进器 I | 改变诊断顺序、补丁算子、经验检索和搜索资源分配 | 后续迭代更容易找到有效 harness 修改 |

最初允许编辑版本化的工作流配置、上下文 builder、工具 adapter、技能程序和策略模块；先将大段编排拆成可组合组件，再扩大源码修改范围。允许受限代码修改是能力形成的一部分，不能永远限制为现有 DSL 字面量组合。

任务定义、外部标签、结果口径与部署接受接口保留在外部边界。边界的目的，是让系统专注于改善解决问题的方式，而不是靠改变“何为正确”获益。

## 3. 先诊断“为什么不会”，再决定改什么

### 3.1 给 improver 可操作的自身观测

在现有 proof 上增加结构化执行轨迹：每个节点拿到了什么输入、舍弃了哪些证据、调用了什么工具、产出了什么结构化中间结果、下一节点采用或忽略了什么，以及消耗和错误状态。

这些记录来自可观测输入输出和调用事件，不要求获取模型隐藏思维。improver 读取相关源码、节点接口和局部轨迹，生成最多几个竞争假设，例如“证据未检索到”“证据存在但单位未对齐”“判断正确但路由丢失”。

### 3.2 用诊断干预找有收益空间的修改点

| 局部试验 | 如果结果改善，下一步优先修改 | 如果仍不改善 |
| --- | --- | --- |
| 在开发案例补入真实、相关的证据片段 | 检索或上下文构造 | 检查理解、推导及任务定义 |
| 用审核过的 claim 分解替换自动分解 | claim 提取技能与上下文结构 | 检查后续证据绑定与判断 |
| 显式执行计算或状态解析后交给判定器 | 新工具及其调用策略 | 检查结果是否被正确使用 |
| 强制执行一次专用检查而非通用再投票 | 路由和工作流 | 检查专用能力本身是否充分 |
| 把已经正确的阶段结果传入原本失败的后续流程 | 接口、状态管理与阶段交接 | 检查下游推理或裁决处理 |

这些试验是开发侧定位工具。人为提供正确中间结果只能说明可能的改进空间，不能部署时依赖它；要把该中间结果转化为可自主获得的过程后，才形成能力。

优先处理出现频繁、影响大、局部替换有改善迹象且实现成本适中的瓶颈。允许调查单个高价值失败，不必等凑出多个共现案例后才学习；随后再用近邻和正常案例形成任务族。

### 3.3 让反馈指向具体改动

反馈对象建议包含：`hypothesis`、`affected_nodes`、`observed_difference`、`missing_precondition`、`next_probe`、`expected_transfer`。例如“触发率为零”应进一步区分输入字段不存在、值被截断、条件过窄、目标节点不可达。不同原因对应不同补丁，不能统一交给模型“再写一条”。

## 4. 能力发现的关键：先试做成功，再编译成技能

### 4.1 给困难案例一个预算受限的探索模式

当当前版本处理失败时，improver 在开发工作区读取案例及必要反馈，检索已有技能，尝试补充证据、分解问题、调用计算工具、改变阶段顺序或编写 adapter。每步必须产生可观察的新信息或测试一个明确假设。

探索模式可以比正常检测昂贵，因为目标是发现可复用的处理过程；预算内连续尝试不产生信息时应切换假设或结束。更多反思和更多同质投票不自动带来能力。

对于开放事实，探索需要可获得的可信资料或冻结来源；如果历史任务所需事实无法取得，应记录信息缺口。系统不能靠自我反思创造缺失事实。

### 4.2 从成功过程提取“如何做”

一条案例被修好之后，improver 做程序化压缩：

1. 找到真正带来改变的证据、工具和步骤，删除无贡献分支。
2. 将具体人名、数值、任务 ID 替换为类型化输入和前提。
3. 把重复操作编译为程序或明确的操作流程，将所需信息放入接口。
4. 写出调用条件、退出条件和失败时的回退路径。
5. 在没有原案例答案提示的近邻任务上尝试复用；失败处决定再次修订还是缩小适用域。

压缩产物可以是一个新工具、一个多步技能、一种上下文构造器或一个路由补丁。新谓词只是其中较简单的一类。

### 4.3 三类经验分别持久化

- **情景经验：** 具体失败与解决轨迹，用于诊断和提示检索。
- **程序性技能：** 可装载、可调用、带接口的解决过程，直接改变执行行为。
- **改进经验：** 哪类瓶颈适合哪种补丁，哪些修改常引入什么退化，帮助下一轮选择搜索方向。

检索按任务需求和失败机制进行，每次只加载少量相关项。频繁调用且稳定的长技能进一步压缩成短流程或程序；重复技能合并，低贡献技能退役，保留依赖关系。这样能力库增长不会简单变成越来越长的提示词。

## 5. 将固定检测链演化为围绕证据缺口的工作流

保持现有检测器作为初始可运行版本，逐步引入显式任务状态：`claims`、`evidence`、`unresolved_questions`、`hypotheses`、`budget_remaining`。这是一份工作数据结构，不能把“已填字段”当成真实完成。

例如一个工作流变体可以是：

```text
提取与任务结果有关的 claims
  → 为每个 claim 绑定已有证据与来源
  → 标注缺口：数值推导 / 外部事实 / 操作状态 / 时序 / 隐含前提
  → 检索并执行适用技能
  → 新证据改变哪一个 claim，就只更新该 claim 的状态
  → 将确有争议的 claim 连同证据交给现有听证
  → 汇总结果；预算耗尽且证据不足则保留未决
```

这只是待搜索的一个起点，并非要求所有任务增加完整 claim 链。简单任务可以走原路径，长轨迹或多断言任务再调用分解。claim 提取本身可能遗漏，因此需要覆盖检查或回退。

改进 agent 的工作流操作应包括：插入节点、替换节点、改变证据连接、添加条件分支、拆分任务、合并冗余检查、改变停止条件。每次补丁都声明修改理由和预计改变的中间行为。

最小节点接口可设计为 `run(state, tools, budget) -> state_delta, events`，工作流通过版本化图和有界状态转移执行。节点只获得所需工具权限，循环具有预算上限。现有 judge、recall、tracer、defense 可以先包装为节点，不必一次重写所有逻辑。

## 6. 真正持续的进化：继承当前版本，并移动学习任务

### 6.1 当前残余错误驱动下一代

每轮主任务从 `H_t` 的未解决问题中选取，同时混入已掌握任务与正常近邻，保护旧能力。新技能生效后，下一轮减少已解决失败族的搜索份额，将资源移向后继难题。

任务课程按依赖展开：先处理单证据数值问题，再加入单位转换，再加入多步运算与干扰证据；先解决明确工具成功状态，再处理多工具依赖。课程变异服务于发现适用边界，不能替代真实任务来源。

### 6.2 存档保存可继续工作的分支

每个候选版本保存父代、补丁、依赖、修好/破坏的行为、适用域与失败反馈。父代选择兼顾已有收益、行为差异和待解决瓶颈。局部有进展的版本可以继续修复，部署版本仍有独立选择过程。

还要允许组合互补能力。例如证据定位工具与数值核验工具分别不改变终态，但串接后可能形成完整证明；如果要求每个组件独立带来最终准确率增益，就会丢掉这种组合路径。组件先以接口能力和局部目标进入研究存档，组合后的完整流程再承担任务级收益责任。

### 6.3 每次迭代后做集成和简化

成功补丁必须更新可装载的 harness manifest，包含工作流、工具和技能版本、检索索引及策略；下一轮按该 manifest 启动。记录哪些任务实际调用了新增能力。

若规则冲突，优先明确适用条件或整合成统一工具；若一个通用技能替代多条特例，删除重复路径。自我改进包括减少冗余、降低上下文负担与修复自身结构，不只增加组件。

### 6.4 自举发生在改进器也用上新能力时

检测阶段获得的工具，应通过共享能力目录向 improver 暴露。例如证据对齐工具既帮助检测，也帮助 improver 更快定位后续错误；轨迹差异分析器既诊断候选，也能发现自己的信息缺失；成功修复模板可以指导下一轮选取补丁。

这形成具体的正反馈路径：

```text
更好的工具/上下文
  → 更准确地理解任务和自身失败
  → 更有针对性的修改
  → 形成更多可复用能力
  → 下一轮改进的成本下降或成功率提高
```

正反馈是否出现需要观察；新工具也可能误导诊断，因此改进器使用它时保留来源与失败状态。不能只让 improver 读取自己的“成功总结”。

## 7. 改进器本身如何改善

不必把全部元层改进推迟到所有检测能力完善之后。第一版就应保存改进经验，并让 improver 使用已有工具；在取得可重复的局部修复后，再小范围开放其自身策略编辑。

优先修改三处：

1. **诊断策略：** 某类问题先检查哪项输入、运行哪种局部试验，可减少盲目生成补丁。
2. **修改策略：** 在提示调整、上下文重构、工具创建、工作流重排之间选择，必要时组合。
3. **搜索策略：** 何时继续修同一分支、检索其他父代、尝试互补组合或停止。

例如多次发现“改提示无效，而加入明确单位变换后有效”，应保存这个适用条件，并在后续数值错误中优先检查单位与计算工具，而不是再次从通用提示改写开始。

实现上，improver 修改的是可版本化的策略程序及模板；候选策略从相同父代和经验起点出发运行有限开发任务流，比较其产生的后代能力与总成本。通过后，新策略真正成为下一轮 improver 的执行版本。这样才形成“改善改进过程”的闭环。

底座权重冻结时，本文将其称为 harness 层面的递归自改进，不外推为模型内在能力无限增长。[STOP](https://arxiv.org/abs/2310.02304)提供了让改进程序改进自身的相关先例，也明确讨论了模型未改变时的 RSI 边界。

## 8. 一个两代能力增长的具体例子

以下为设计示例，不是仓库已取得的结果。

**起点：** 工具给出同币种 12 与 18，agent 回答平均值为 16；当前检测器仅凭文本整体观感漏检。

**第一次改进：** improver 对比“再问一次 judge”和“显式构造运算并执行”两种处理过程。后者定位到正确结果 15，于是将实体绑定、操作数提取、计算、结果回传编译成 `numeric_derivation` 技能。它同时加入正确平均值、缺操作数、不同币种等近邻，形成适用与回退条件。工作流在含数值推导的 claim 上调用该技能，不要求每个答案都运行它。

**第二次改进：** 当前版本能查平均值，但遇到跨单位总量仍失败。巡检从这个新残余错误出发，复用已有操作数与计算链，创建单位归一化工具，再组合进同一技能。系统没有重新从“数字未出现在工具输出里”开始猜规则。

**对 improver 的收益：** 两代修复过程保存为“数值错误先检查实体、单位和运算关系”的诊断程序；后续搜索直接调用该程序和计算工具。其价值是减少重复探索，并让新的复合问题进入可解决范围。

这里分别发生了：执行过程变化、程序性能力积累、学习任务推进和改进策略复用。只有第一项发生时，应称为一次 harness 优化；后几项持续发生，才有理由讨论累积自改进。

## 9. 验证作为支撑：保留必要边界，不主导方案

验证分成两种用途：开发过程中用局部试验提供具体反馈；候选集成时用独立任务判断是否值得保留。开发反馈必须足够丰富，只有“通过/拒绝”难以支持学习。

必要边界保留如下：

- 当前已有 693 例的历史暴露不能靠重新划分消除；开发、重复回归、有限次数晋升验证与最终终审应区分。测试反馈不回流同一独立测试集的后续搜索。
- 检测器谓词、模型自信和多模型一致不能自产 gold。可形式化的子任务用独立参考实现；开放事实依赖可信来源或人工标注；资料缺失保留 unknown。
- 代码变异在隔离工作区和受限进程运行，不能写标签、评分器或提交凭据；哈希账本负责追溯，不替代权限隔离。
- 记录 FP/FN/U、证据定位、成本以及新增能力的实际调用；控制重抽与缓存失配。局部回放便于诊断，最终版本需真实端到端运行。
- 将固定技能库、等预算一次性搜索、每轮清空经验、只改提示和完整闭环比较。统计单位按独立任务及来源分组，不能把重复调用或模板变异当成独立样本。

本方案最关键的观察量是：**当前版本的新残余错误是否被修复、后代是否真实复用祖先能力、后续修改是否更省资源，以及旧能力是否保留。** 若只有更高分而没有继承使用记录，不能直接归因于递归机制；若只有工具与记忆增多而真实任务未改善，也不算能力增长。

## 10. 当前项目应当先改什么

不再以“先建大型 oracle 套件”为主线。优先完成一个能自主调查、编写、运行并继承改动的最小 improver，让它解决一个真实可定位的 harness 瓶颈；必要验证与之同时建设。

| 顺序 | 具体落点（新增名称为建议） | 必须产生的行为变化 |
| --- | --- | --- |
| 1. 改进对象对齐 | 修改 `evolution/engine.py`，主 patrol 使用当前 active 版本；保留裸底座对照 | 下一轮面向上一轮剩余问题，而非重复生成裸底座补丁 |
| 2. 使 improver 能调查和动手 | 新增 `evolution/improver.py`、`diagnostics.py`，复用 `worksheet.py`、checkpoint 和现有后端；提供读源码、编辑限定文件、局部执行工具 | 从失败到局部假设、试验、实际补丁，再到结果修订 |
| 3. 开放高价值修改面 | 先支持上下文 builder、工具 adapter、技能和路由配置；将 `detector/api.py` 中相关阶段包装为可组合节点 | 允许改变证据流和处理步骤，不局限于既有谓词组合 |
| 4. 编译与继承能力 | 新增技能描述、`archive.py` 与 harness manifest；扩展 registry 的版本装载接口 | 成功处理过程变为下轮实际执行的工具/技能；依赖可追踪 |
| 5. 推进课程并整合 | 开发池按当前残余错误、旧能力回归、正常近邻组织；定期合并冗余技能 | 任务随能力成长推进，技能库不会无限堆叠 |
| 6. 开放小范围元策略修改 | 将诊断、补丁算子选择、修订策略版本化；在 `meta_eval.py` 等位置接入后代运行比较 | 已学会的经验改变后续改进方法 |

现有 DSL、四类干预、阶段回放、registry 与 ledger 都继续复用；它们分别成为补丁语言、执行接口和持久化设施。checkpoint 的存在可支持工作过程恢复，旧实验缺少完整提案时仍不能精确恢复。此次仅修改方案，不改动这些代码。

### 首个可交付闭环

选择一个有可靠来源、正常近邻和明确局部瓶颈的开发失败。让 improver 自主完成“读取轨迹及代码→提出局部诊断→尝试不同处理过程→写出可执行改动→形成技能并装载”。随后给它第二个相关但不同的任务，检查它是否利用第一轮能力继续修改。

初期可以限制每轮只改一个子图或一种工具，每个分支至多两次修订，总调用与时间预算固定。这些是探索起点，不是通用最优参数。第二轮若仍从零开始、旧技能未被调用、或改动只存在于文字总结，优先修继承与装载链路，继续增加候选数没有针对性。

### 何时换方向

| 观察到的问题 | 对应动作 |
| --- | --- |
| 补充正确中间信息后仍不能解决局部任务 | 检查任务分解与底座能力上限；必要时换工具或模型，停止反复改提示 |
| 探索模式能解决，但技能化后失效 | 修上下文接口、前提抽取和程序压缩，保留必要步骤 |
| 单个技能有效，组合后退化 | 查证据对象、状态覆盖和路由冲突；做组合简化 |
| 改进反复围绕已解决问题 | 查 active 巡检、经验检索和课程更新是否真正生效 |
| 后代大量重用旧组件但新任务无改善 | 查组合是否增加新处理能力，或任务是否已超出现有信息和工具边界 |
| 改进器成本持续增长 | 压缩频繁技能、删除冗余流程、停止低产分支，比较简化固定方案 |

## 11. 研究依据与项目区别

以下是一手来源支持的机制借鉴；具体项目设计是待验证的迁移，尚不构成新颖性结论。

| 工作 | 与本方案相关的机制 | 本项目的具体落点 |
| --- | --- | --- |
| [SICA：A Self-Improving Coding Agent](https://arxiv.org/abs/2504.15228) | agent 使用编程工具编辑自身系统，通过代码更新改善任务表现 | 给 improver 实际工作区和编辑执行组件的能力 |
| [DGM](https://arxiv.org/abs/2505.22954) | 自修改、经验评估和从多样 agent 存档采样 | 继承可执行父代、保留分支与部分进展 |
| [STOP](https://arxiv.org/abs/2310.02304) | 用改进程序改善改进程序本身 | 让诊断和修改策略的变化真正接入下一轮 |
| [Reflexion](https://arxiv.org/abs/2303.11366) | 利用反馈形成语言反思并保存情景记忆 | 将经验检索作为起点，再把稳定处理过程编译成技能 |
| [ADAS](https://arxiv.org/abs/2408.08435) | 基于历史存档编程 agent 及其组件和流程 | 将上下文、工具与工作流组合纳入搜索 |
| [FunSearch](https://www.nature.com/articles/s41586-023-06924-6)、[AlphaEvolve](https://arxiv.org/abs/2506.13131) | 程序搜索结合自动评估 | 为可执行局部能力提供快速反馈，而不将全部幻觉判断化约为确定性规则 |

本项目值得研究的具体问题是：**面对长轨迹、证据不完整和多阶段误差，Harness Agent 能否把一次失败中的成功调查过程转化为可迁移的工具与工作流，并用这些能力改善下一轮调查和自我修改？** 若这一链条成立，验证器负责确认结果，能力增长则来自系统对自身信息处理和行动方式的持续重构。
